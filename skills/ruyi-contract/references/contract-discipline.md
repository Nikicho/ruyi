# Contract Discipline

## 1. 目标

contract 阶段负责把用户意图转成可实现、可验收、可追踪的业务约定。

它吸收 Superpowers `brainstorming` 和 `test-driven-development` 的核心约束：先理解目标，先形成设计边界，先定义自然语言测试用例，得到用户确认后再进入 plan。

## 2. 硬门禁

- 没有明确业务目标，不落 contract。
- 没有验收标准，不进入 plan。
- 没有自然语言测试用例，contract 不能标 `confirmed`，也不进入 plan。draft 阶段允许占位但不能完全为空。
- 测试用例必须能逐条映射回至少一条验收标准。
- 测试用例必须用业务语言描述用户路径、输入、预期结果或边界场景；不写自动化实现细节。
- 涉及接口时必须写 `## 接口范围`，但不抄完整 API 文档。
- 没有用户确认，不把草稿 contract 视为已确认需求。
- 需求仍在发散时，不进入 plan。
- 修复类需求事实不清时，先进入 `debugging-discipline.md`。
- 修复类 contract 必须写明问题现象、影响范围和验证方向，不能把根因猜测写成结论。
- 重构类需求必须说明业务价值或风险收益，否则不能只因“代码不优雅”进入正式开发。
- 需求过大时，先拆分为多个 contract 或在 plan 阶段拆为多个 task，不写巨型 contract。

## 3. 最小流程

1. 读取 `.ruyi/spec/INDEX.md`，再按索引读取项目 spec 和可用 team spec。
2. 按 confidence 折扣规则处理 spec 内容。
3. 判断需求类型：新功能、修复、重构、需求调整。
4. 用一句话写清业务目标。
5. 一次只追问当前最关键的缺口。
6. 写出用户故事。
7. 写出验收标准。
8. 写出自然语言测试用例。
9. 明确范围内和范围外。
10. 向用户确认 contract。
11. 确认后才允许进入 plan。

## 3.1 confidence 折扣规则

agent 在 contract / plan 阶段引用 spec 内容时，必须按 confidence 处理：

| confidence | 处理 |
| --- | --- |
| `observed` | 可直接引用 |
| `confirmed_by_user` | 可直接引用 |
| `distilled` | 引用前必须告知用户“此事实来自蒸馏，需要确认”；用户认可后视为 confirmed_by_user |
| `claimed` | 必须在本次 contract 阶段二次确认；不能作为既定事实使用 |
| `open` | 不能引用作为事实；遇到时必须先问用户 |

## 4. 输出边界

contract 可以包含：

- 用户故事
- 验收标准
- 自然语言测试用例
- 范围内/范围外
- 业务对象和模块归属
- 需求类型
- contract 日期
- 接口范围（仅当本次涉及接口）
- 修订记录（仅当中途变更类型 A/B）

contract 不应该包含：

- 详细代码方案
- task 拆分
- 自动化测试实现细节
- 临时调试过程
- 审批结论
- 长篇技术规范
- 与本次需求无关的历史背景
- 完整 Swagger / OpenAPI / Apifox 字段拷贝
- mock 数据正文

当用户开始讨论组件拆分、状态管理、缓存、service 组织、mock、错误处理、目录调整或实现步骤时，先提醒这是 plan 阶段内容。

contract 阶段只确认这些话题是否形成业务约束或验收要求：它是否影响用户行为、兼容范围、性能目标、安全边界或交付范围？

- 如果影响，把影响写成业务规则、范围边界、接口范围或验收标准。
- 如果不影响，不写入 contract，留到 plan 阶段讨论。

## 5. 反模式

| 反模式 | 正确处理 |
| --- | --- |
| “这个很简单，直接做” | 简单需求也要至少确认目标和验收标准 |
| 用户描述 UI 细节后直接实现 | 先确认它背后的业务结果 |
| 把技术方案写成 contract 主体 | contract 写业务约定，技术方案留给实现阶段 |
| 把测试自动化方案写进 contract | contract 只写自然语言测试用例，自动化策略留给 plan/test |
| 修复类需求只写“修复 bug” | 写清现象、影响范围、复现或证据 |
| 重构类需求只写“优化代码” | 写清业务风险、维护收益或交付约束 |
| 把完整 Swagger JSON 抄进 contract 或 spec | 只引用后端权威源，contract 只列本次接口范围 |
| 接口字段变化只改代码不动 contract | fix/change contract 的 `## 接口范围` 记录字段变化和影响范围 |

## 6. 具体反模式（Anti-patterns）

### ❌ 用户说“要个搜索”，我就猜 5 条验收标准

**触发场景**：用户只给了模糊目标，比如“加个搜索”。

**你想做的事**：直接补齐一套看似合理的验收标准让用户确认。

**为什么错**：这是替用户定义需求，容易把猜测伪装成澄清。

**正确做法**：一次只问一个最关键问题，例如“搜索范围是订单编号、客户名称，还是所有可见字段？”

### ❌ fix 类需求，用户描述了现象，我直接给根因

**触发场景**：用户说“点击保存没反应”“筛选不生效”。

**你想做的事**：直接判断是接口、状态或组件问题。

**为什么错**：没有证据链，根因只是猜测。

**正确做法**：先记录问题现象、影响范围、复现或验证方向，再进入修复设计。

### ❌ 需求很大但用户着急，我写一个巨型 contract

**触发场景**：一个需求覆盖多个模块、多个角色或大量验收标准。

**你想做的事**：把所有点塞进一个 contract，避免打断用户。

**为什么错**：巨型 contract 会让 plan 和 test 不可控。

**正确做法**：拆成多个 contract，或至少标记为 `large` 并强制 plan 拆 task。

### ❌ 业务目标和验收标准都写了，测试用例段空着先标 confirmed

**触发场景**：用户对验收标准已确认，agent 想尽快推进到 plan。

**为什么错**：验收标准是二元判定，测试用例是具体场景化预期行为。没有测试用例时，plan 阶段无从制定测试策略，test 阶段无从对照验收。

**正确做法**：在 confirmed 前一次只问一个测试场景缺口，例如“搜索关键词为空怎么办？”、“结果为零怎么显示？”，逐条补全测试用例后再 confirmed。

### ❌ 测试用例只覆盖 happy path

**触发场景**：用户描述了主要场景，agent 写了 1-2 条测试用例。

**为什么错**：边界和异常路径是 contract 测试用例最有价值的部分，缺失会导致 implement 和 test 阶段都漏。

**正确做法**：每个验收标准至少配一条正常路径用例，并补充边界或异常用例；standard / large 默认至少覆盖正常、边界、异常三类。

### ❌ agent 自己判断“这是非语义变化”

**触发场景**：用户说“加个按钮”，agent 不和用户确认就原地改 contract。

**为什么错**：分类判断包含业务理解，agent 容易低估影响。

**正确做法**：先输出分类判断，等用户确认后再执行。

### ❌ 静默覆盖已 done 的 task

**触发场景**：类型 B 变更时，agent 直接把 task-2 的内容改写成新需求。

**为什么错**：历史不可追溯；如果新需求又被撤回，旧实现状态丢失。

**正确做法**：重评 plan；若本地 checkpoint 不再有效，删除并按当前 plan 重建。

### ❌ 审批后通过修订原 test 绕过重新验收

**触发场景**：test 已 approved，用户说“上线前加个埋点”，agent 把埋点写进原 test。

**为什么错**：approval 是事实，被改写后下次复盘无法判断当时通过的到底是什么。

**正确做法**：走类型 D，重开同一 contract，记录返工原因并重新验证、审批。

### ❌ 类型 C 不新建文件，硬改原 contract

**触发场景**：用户改了核心业务规则，agent 在原 contract 里覆盖。

**为什么错**：旧 contract 的语义彻底丢失，plan / test 引用关系混乱。

**正确做法**：新建日期 contract；旧 contract 加 `superseded_by`，plan / test 跟着新建。

### ❌ 修订时不更新 INDEX

**触发场景**：类型 B 改完 contract 和 plan，但忘了刷新 INDEX。

**为什么错**：INDEX 失同步；agent 下次靠 INDEX 找历史时被误导。

**正确做法**：所有写入脚本末尾触发 INDEX 重建，或在脚本不可用时明确提示人工重建。

## 7. 检查清单

落盘前检查：

- 是否有明确模块或业务对象？
- 是否有一句话业务目标？
- 是否有用户故事？
- 是否有可验证的验收标准？
- 是否有自然语言测试用例？
- 是否明确范围外？
- 是否知道这是新功能、修复、重构还是需求调整？
- 如果是修复，是否已有足够问题事实？
- 是否已经由用户确认，可以标记为 `confirmed`？

任何一项缺失，都不要进入 plan。
