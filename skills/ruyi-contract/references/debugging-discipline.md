# Debugging Discipline

## 1. 目标

修复类需求必须先确认事实和复现路径，再决定 contract 和实现边界。

它吸收 Superpowers `systematic-debugging` 的核心约束：不要猜，不要碰运气，先形成可解释的证据链。

## 2. 硬门禁

- 没有现象描述，不进入修复实现。
- 没有复现步骤、失败日志、截图、测试失败或可观察证据时，不把猜测写成事实。
- 未验证根因前，不声称“问题是因为...”。只能写“当前假设是...”。
- 同一轮调试只验证一个主要假设。
- 修复方案必须能解释已观察到的现象。
- 无法定位根因时，必须记录未确认项和下一步验证，而不是强行生成确定结论。

## 3. 最小流程

1. 描述问题现象。
2. 明确影响范围和严重程度。
3. 收集复现步骤或失败证据。
4. 提出最可能假设。
5. 验证该假设。
6. 根据证据调整假设或确认根因。
7. 把确认后的修复目标写入 contract。

## 4. 证据类型

可接受证据包括：

- 稳定复现步骤
- 浏览器控制台错误
- 构建或测试失败日志
- 网络请求和响应异常
- 用户截图或录屏
- 明确的代码路径和状态变化

不可接受证据包括：

- “应该是这里”
- “看起来像”
- “先改了试试”
- “以前也有类似问题”

## 5. 反模式

| 反模式 | 正确处理 |
| --- | --- |
| 同时改多个可疑点 | 每次只验证一个主要假设 |
| 看见报错就改最近的代码 | 先确认报错与问题现象之间的关系 |
| 修复后不验证原问题 | 必须用原复现路径或等价证据验证 |
| 根因没确认就写 test 结论 | 返回 debugging 或 test，不能进入 test 结论 |
| 把临时猜测沉淀进 spec | 未验证内容只能进 open questions 或任务记录 |

## 6. 检查清单

进入修复实现前检查：

- 是否能描述用户看到的问题？
- 是否知道影响哪些场景或模块？
- 是否有复现路径或失败证据？
- 是否有当前假设？
- 是否验证过该假设？
- 修复目标是否能写成 contract 的验收标准？

缺少证据时，可以继续调查，但不能进入正式实现。
