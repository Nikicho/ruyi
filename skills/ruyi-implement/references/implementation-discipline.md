# Implementation Discipline

## 1. 目标

实现阶段负责按 plan 完成代码变更、task 执行、自检和代码质量收口，并为测试阶段提供可验证结果。

它吸收 Superpowers `executing-plans` 和 `test-driven-development` 的核心约束：按计划执行、失败不跳步、实现前后都对照验证点。

`using-ruyi` 可以把代码优化、代码微重构等无行为变化请求路由到轻量维护模式。轻量维护模式仍属于 implement 阶段，但不属于单次需求主流程。

## 2. 硬门禁

- 没有 contract 或等价需求定义，不进入正式实现。
- 没有 plan 或等价实施计划，不进入正式实现。
- 轻量维护模式不要求 contract / plan / task，但必须由 `using-ruyi` 明确路由进入。
- 轻量维护模式必须确认不改变业务行为；如果发现用户可感知行为、业务规则、接口语义、状态语义、权限、路由或验收标准变化，必须返回 contract。
- 没有读取相关 project spec，不进入正式实现。
- 实现前没有明确验证点，不开始编码。
- 能写自动化测试的场景，应优先补测试或先定义可执行验证方式。
- 如果发现 contract 不足，返回 contract 阶段补充，不在代码里隐式扩大范围。
- 如果发现 plan 不足，返回 plan 阶段补充，不边写边补计划。
- 未完成代码自检和必要优化，不进入 test。
- 标记 task 为 `done` 前，必须写出自检与 review 结论。
- 未经过 test 阶段验证，不声称完成。

## 3. 最小流程

1. 读取 contract。
2. 读取 plan 和 task。
3. 读取 project spec 和可用 team spec。
4. 按 plan 判断影响范围和相关模块。
5. 对照 plan 中的测试策略确认验证点。
6. 实现最小必要改动。
7. 运行局部验证。
8. 完成代码自检、review 反馈处理和必要优化。
9. 交给 test 阶段完成验证收口。

轻量维护模式最小流程：

1. 明确维护目标和写入边界。
2. 确认不改变业务行为。
3. 读取相关 project spec 和可用 team spec。
4. 实施最小代码优化或代码微重构。
5. 运行可行的局部验证。
6. 完成代码自检和 review 反馈处理。
7. 判断是否发现可沉淀规范；如有，只提示用户后续单独进入 spec-evolve，不自动生成 spec-candidate。

## 4. 验证点要求

验证点必须来自 contract 的验收标准和 plan 的测试策略。

一个有效验证点应该说明：

- 验证什么行为
- 通过标准是什么
- 使用自动化测试、命令、页面操作还是人工观察
- 如果当前无法验证，原因是什么

## 5. 反模式

| 反模式 | 正确处理 |
| --- | --- |
| 边写边重新定义需求 | 返回 contract 修订 |
| 边写边重新制定计划 | 返回 plan 修订 |
| 为了顺手重构扩大范围 | 只做 contract 内必要改动 |
| 先写完再想怎么测 | 实现前先列验证点 |
| 代码能跑就说完成 | 进入 test 阶段，用证据收口 |
| 发现技术债就直接改 | 记录为技术候选，不混入本次需求 |
| 不做代码自检就交付 | 先完成 implement 阶段自检和优化 |
| 轻量维护时发现行为变化还继续改 | 停止并返回 contract |
| 维护结束后直接写 spec-candidate | 只提示可沉淀规范，是否沉淀由后续流程决定 |

## 6. 具体反模式（Anti-patterns）

### ❌ task 只写 OrderList.vue，我顺手优化 OrderItem.vue

**触发场景**：你发现相邻组件也“不太优雅”。

**你想做的事**：顺手重构或改样式。

**为什么错**：写入边界被破坏，review 和验证范围都会失真。

**正确做法**：停止越界改动；如果确实需要，返回 plan 扩大写入范围。

### ❌ test 还没跑，但代码看起来对，我先报告完成

**触发场景**：代码实现很小，手动看起来没有问题。

**你想做的事**：直接说“完成”或跳过 test。

**为什么错**：完成声明必须有验证证据。

**正确做法**：进入 `ruyi-test`，记录命令、UI 操作或手工验证证据。

### ❌ lint 有 warning，应该不影响功能

**触发场景**：验证命令有 warning 或部分失败。

**你想做的事**：口头判断“不影响”。

**为什么错**：没有记录输出和影响判断，后续无法审计。

**正确做法**：记录实际命令、结果、warning 内容和是否影响验收。

## 7. 检查清单

编码前检查：

- 是否有明确 contract？
- 是否有明确 plan？
- 如果是轻量维护模式，是否明确维护目标、写入边界，并确认不改变业务行为？
- 是否读取了相关 spec？
- 是否知道本次影响哪些模块？
- 是否明确至少一个验证点？
- 是否判断过能否补自动化测试？
- 是否确认本次不会改范围外内容？
- 是否安排了代码自检和必要优化？
- 是否判断本次是否发现可沉淀规范？

如果不能回答这些问题，不要开始编码。
